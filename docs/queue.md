# Durable request queue

`Application.handle` admits fresh requests immediately, including while Codex is working. `monitor_status` reads local progress without contacting Telegram or Codex. Each accepted account/group/message identity receives one immutable SQLite admission sequence; dispatch uses that order across all project groups. Duplicate deliveries never create a second request. Editing an old message into a request remains ineligible.

Execution ownership covers the canonical state database path using a nonblocking OS file lock, shared by automatic dispatch and manual commands. Separate application instances and processes using the same state return `busy` while an execution owns that lock. Admission and local status remain available. Never delete or replace the `.execution.lock` file while applications use the state directory. OS ownership releases on process exit; a retained `running` or `uncertain` request blocks later dispatch and manual execution until its external outcome is reconciled by recovery, rather than assuming process exit stopped Codex.

At execution start the worker rechecks current folder access, the trigger's existence and marker, the current project assignment, and any existing topic/chat binding. Confirmed trigger deletion or marker removal cancels pending work without a Codex action. Network failure reading the trigger blocks it; it does not prove deletion. Incomplete selected history and required input failures also block execution.

The trigger ID is the fixed context upper boundary. Telegram history RPCs use `max_id=trigger+1` on every page, so later replies and attachments are not fetched as this request's history. The current text and attachments through that boundary are captured when execution starts. Saved `input-N.txt`, `context-N.json`, original files, and input manifests belong to that run. Edits before capture are included; edits during a run and later messages can enter a subsequent request only. A topic's later request continues its existing Codex chat and task folder.

`monitor_status.requests` exposes admission sequence, source, status, task ID when assigned, and terminal outcome. The worker stores the explicit request-to-task binding before attachment capture or external Codex effects. Pending admission and completed outcomes survive reconstruction from the same database/task directory. A failed create/execute with an unknown remote outcome is retained as `uncertain`; a crashed `running` request remains unresolved; this ticket does not replay unknown chat/turn outcomes, reconnect history, or implement interruption/recovery (tickets 10–13). Telegram send reconciliation belongs to ticket 14.

Verification uses the public application interface, real SQLite/task files and external Telegram/Codex substitutes: concurrent admission/status, shared-state process exclusion and crash release, ordered same-chat continuation across restart, corrections before execution, frozen running input, later-message exclusion, cancellation, missing-trigger transport failure, and incomplete required context. Thin Telegram adapter checks verify actual history RPC bounds and typed deletion evidence. Ticket 09 did not start a live Telegram client or create a live Codex turn; ticket 08's genuine human-trigger live evidence remains the integration foundation.
