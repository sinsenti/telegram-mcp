# Recovering missed Telegram requests

The listener calls the shared `monitor_catch_up` application command after its initial `client.catch_up()` and on each 30-second monitoring refresh. The latter also covers Telethon automatic reconnections and laptop sleep: after network access returns, the next successful pass resumes the application cursor. Telethon's persisted update cursor and this application's durable history cursor are separate. Neither replaces the other.

Each call reads at most one page per currently ready allowed group (default 100 messages; `page_size` accepts 1–100). A full page returns `possibly_more: true`; subsequent passes retain and drain the backlog. Pages use scoped `messages.getHistory`, never global account search. Folder membership is rechecked before every page and before committing admission. Explicit folders keep their direct selected-peer path.

History proceeds from the oldest available message after each saved group cursor, independently of newer live events. Across one discovered batch, requests sort by creation timestamp then stable group/message identity. They append to durable admission order; older late discoveries cannot reorder previously pending or running work. Admissions and page cursors commit in one SQLite transaction without suspending for network operations. Failed batches roll back together. Duplicate keys, including completed requests, never create a second request.

Original activation cutoffs remain unchanged on reconnect or process restart. Removing and re-adding a group establishes fresh readiness and a fresh cutoff; earlier backlog and paused work do not automatically start.

A history response contains current text, not an authenticated original version. Unedited history can establish a posted marker; edited offline history cannot establish whether the marker existed originally. Such messages cannot create requests. `monitor_status.catchup_uncertainties` and the catch-up response expose the excluded identities and explanation durably. Previously recorded pristine new-message observations and admitted requests remain intact; edited observations never overwrite that evidence. This deliberately excludes some legitimate requests that were edited while offline. A fresh request is the safe way to proceed.

Verification covers the shared Application with real SQLite/task files, reconstruction, multiple groups, bounded pages, durable order, rollback, duplicate completed work, new readiness, and conservative edited-history exclusion. A focused Telethon adapter test checks actual request classes, reverse-history offsets and access removal, and a listener check verifies initial SDK catch-up precedes application discovery. No live disconnection/sleep history scenario was performed for this ticket.

A bounded read-only live adapter check against the authorized test group fetched messages 36–37 after cursor 35, then messages 38–39 after cursor 37, using two explicit pages of two. Creation timestamps and `history_message`/edit metadata were preserved. No application admission, Codex turn, or send occurred, and the connection was closed. Evidence: `.scratch/telegram-integration/catchup-history-live-test.json`. This validates actual Telegram forward pagination, not a live automatic sleep/reconnect execution scenario.
