# Attachment inputs

Manual task/followup commands preserve selected Telegram originals alongside each captured run. The connector downloads opaque bytes; Codex uses its existing enabled interpretation tools. Text, supported images, PDF, Word and spreadsheet format hints come from the filename or recognizable MIME fallback. These untrusted labels never prove readability. Unsupported media without a downloadable original identity blocks with the source message identity.

`read` exposes attachment metadata. An input identity is `<group_id>:<message_id>:<media_id>`. Source display names, original media identities, group/message associations, size and SHA-256 remain in `inputs-N.json` and task status. Storage uses connector-owned `inputs/N/index/original.<known suffix>` paths, so names such as `../../AGENTS.md` and repeated display names cannot overwrite other inputs or activate instruction files. Each follow-up adds a fresh run while retaining previous originals, context and evidence. A failed download retains its partial file with `download_status=failed`; other successful originals remain preserved. Any download blocker prevents chat creation/turn execution.

Unknown-necessity or needed unsupported inputs block after preservation. A caller can explicitly declare an unsupported original unnecessary using `unnecessary_input_ids: ["<group>:<message>:<media>"]` on the task/followup command. This structured caller instruction is the only exclusion mechanism: model guesses and prose in untrusted attachments cannot grant it. Supported inputs cannot be excluded by this command. Exclusions outside the selected context are rejected. The result identifies excluded originals without claiming interpretation.

The app-server receives an absolute-path manifest and `localImage` inputs for images. For PDF, Word and spreadsheets it requests `skills/list` for the actual task folder and passes an enabled applicable skill through the installed protocol's `skill` input. Skill discovery and protocol fields match CLI 0.169.0; the implementation does not invent a general document `localFile` input. Missing skills or unavailable downstream tools produce blockers. Existing model/permission settings remain inherited; an interactive permission decision remains a blocker.

Every original requires structured `input_evidence` containing its exact input identity, outcome and concrete content observation with a useful locator. Missing, duplicate, unknown, empty, unreadable or unauthorized excluded evidence cannot finish the task. The adapter returns parsed terminal results without deciding whether interpretation is sufficient. Before applying interpretation policy, the application retains the turn identity, explanation, result status and evidence in task status, `run-result-N.json` (including the returned Markdown), and `evidence-N.json`. This includes completed turns with invalid evidence and structured blocked results; neither may produce a successful task report. Hashes are checked after successful execution. Originals are instructed to remain unchanged and conversions belong in a separate work directory. Successful Markdown and explanations use the existing source-specific Telegram reporting path.

An explicit `followup` can supply usable input or an unsupported-input exclusion after a blocker during input capture, or after a parsed terminal Codex result has been stored. It keeps the task folder and existing chat, captures a new run, and preserves prior originals and run artifacts. Current-run turn, evidence, result and reporting fields are cleared before the new capture so earlier success cannot appear as evidence for the new request. This is manual continuation, not automatic retry. Unknown chat creation, turn execution, permission or reporting outcomes still require inspection; a lost blocker-report acknowledgment also prevents continuation. General crash recovery remains outside ticket 04.

Path handling rejects symlink ancestors and uses exclusive, no-follow creation of an exact file handle. Telethon receives that handle, never an untrusted filename or output directory. The downloaded destination inode and source metadata are rechecked. This protects against filename traversal and pre-existing path collisions; it is not an isolation boundary against hostile processes running as the same OS user. Agent-reported content evidence likewise is not cryptographic proof of interpretation.
